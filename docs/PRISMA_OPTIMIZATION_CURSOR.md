## 1. Коміт і пуш

Діє правило `.cursor/rules/git-workflow.mdc`. Коротко:

- Після кожного завершеного пункту з розділу 2 роби **окремий коміт** і `git push origin main`.
- Повідомлення пиши українською, конкретно, з емодзі-префіксом. Приклад: `🔧 Журнал: синк лише змінених записів (менше запитів до Prisma)`.
- Після пушу перевір деплой у Vercel. Якщо статус Error, читай build logs, виправ помилку й запуш знову, доки не буде Ready.
- Перед пушем: `cd web && npx tsc --noEmit` (і `npm run lint`, якщо є час). Не пуш код, що не компілюється.
- **Не змінюй** `ALTEGIO_FINANCE_SYNC_START_DATE`, схему Prisma і міграції без окремого обговорення з користувачем.

## 2. Подальша оптимізація (у порядку пріоритету)

Загальний принцип: **cron не повинен перезаписувати в БД дані, які не змінилися.** Кожен `upsert`, `update`, `findUnique` чи `count` — окремий оплачуваний запит. Тому:

1. Прочитай наявні рядки з БД **одним** `findMany` (`where: { id: { in: [...] } }`, `select` лише потрібних полів).
2. Порівняй з даними з Altegio в пам'яті. Для порівняння можна зберігати хеш `rawData` у колонці (наприклад, `rawHash`).
3. Пиши лише нові рядки (`createMany`) і змінені (`update` або батч у `$transaction`).

### 2.1 Журнал записів — `web/lib/journal/index.ts` (cron `sync-journal-records`, щогодини)

**Проблема.** `journalAltegioSyncRange()` бере діапазон від 1-го числа місяця **на 36 місяців уперед**. Для кожного запису в циклі викликається `upsertSalonAppointmentFromAltegio(...)` (кілька запитів на запис). І так 24 рази на добу.

**Що зробити:**
- У `syncAppointmentsRangeFromAltegio` перед циклом один раз завантаж наявні `salonAppointment` за `altegioRecordId in [...]` з полями, які порівнюються (datetime, seanceLength, attendance, staff, deleted, services/коментар). Можна додати й порівнювати хеш.
- Викликай `upsertSalonAppointmentFromAltegio` **лише** для нових або змінених записів.
- Зменш діапазон щогодинного cron, наприклад «сьогодні − 3 дні … +90 днів». Повний діапазон (1-ше число місяця … +36 міс) запускай раз на добу вночі, так само як зроблено для фінансів (див. `resolveDefaultDateFrom` у `sync-altegio-finance-transactions/route.ts`).
- Записи щодня й так оновлюються через вебхук Altegio (`app/api/altegio/webhook`), тож cron — лише страховка.

**Критерій готовності:** у логах `[journal] Sync Altegio …` видно, скільки записів отримано, а скільки реально записано. Друге число в звичайний годинний запуск має бути близьке до 0.

### 2.2 Склад-дзеркало — `web/lib/warehouse/import-from-altegio.ts` (cron `sync-warehouse-mirror`, щогодини)

**Проблема:**
- Для кожного складу виконуються `findUnique` + `upsert`, для кожного товару — `upsert` (усі товари щогодини).
- **Щогодини** скасовуються старі документи `altegio_sync` і створюються нові `warehouseDocument` з рядками. Таблиця документів росте на 24 знімки на добу, а запити множаться на кількість рядків.

**Що зробити:**
- Склади й товари завантажуй одним `findMany`. `upsert` роби лише для нових або змінених (порівняння title, category, groupId, unit, costPerUnit, salePrice, isHair, lengthCm, weightGrams).
- Перед створенням нового знімка порівнюй залишки з поточним `posted`-документом `altegio_sync`. Якщо залишки не змінилися, **нічого не створюй і не скасовуй**.
- Розглянь запуск раз на 3–6 годин замість щогодини (`web/vercel.json`, `"20 * * * *"` → наприклад `"20 */4 * * *"`). Спершу запитай у користувача, наскільки свіжі залишки потрібні.

### 2.3 Архів Altegio — `web/lib/altegio/archive.ts` (cron `sync-altegio-archive`, тепер щогодини)

- Перевір, чи `runAltegioArchiveSlice()` уже повертає `step: "done"` (логи Vercel: `[cron/sync-altegio-archive] Крок`).
- Якщо `done`, запропонуй користувачу **прибрати cron з `web/vercel.json`** взагалі, бо архів одноразовий. Ручний запуск лишається через `scripts/altegio-archive-run.ts` або адмінку.
- Якщо ще не `done`, лиши щогодинний запуск, але в `syncArchiveClients`, `syncArchiveVisits` і `syncArchiveVisitPayments` заміни поштучні `upsert` на `createMany({ skipDuplicates: true })`, де це можливо.

### 2.4 Синхронізація фінансів — `web/lib/altegio/finance-transactions-sync.ts`

Розклад уже виправлено (коміт `c723cb2`). Наступний крок — сам цикл:
- У `syncAltegioFinanceTransactions` для кожного рядка виконуються `altegioFinanceTransaction.upsert` і ще `altegioPaymentPurpose.upsert`.
- Завантаж наявні транзакції сторінки одним `findMany` за `altegioId in [...]` і пиши лише нові або змінені.
- `altegioPaymentPurpose.upsert` роби один раз на унікальний `normalizedTitle` за запуск (збирай `Set`), а не на кожен рядок.

### 2.5 Інші cron з `web/vercel.json`, що працюють кожні 5–15 хвилин

| Cron | Розклад | Дія |
|---|---|---|
| `photo-reminders` | `*/5` | Перевір, чи потрібна така частота. Якщо нагадування погодинні, постав `*/15` або `*/30`. |
| `reports-daily` | `*/5` | Використовує KV (Redis), а не Prisma. **Не чіпай**: від частоти залежить точність часу звіту. |
| `sync`, `reminders`, `direct-reminders` | `*/15` | Переглянь, які запити до Prisma вони роблять на кожен запуск, коли нічого робити. Додай ранній вихід без запитів до БД. |
| `update-direct-states`, `sync-paid-service-dates`, `sync-direct-altegio-metrics`, `sync-last-visit` | щогодини | Ті самі правила: лише змінені рядки, батчі замість циклу з `await`. |

## 3. Як міряти результат

1. **Prisma Console** (Vercel → Storage → база → *Open in Prisma Postgres*) → Usage / Operations. Порівняй кількість операцій за добу до 1.11.2026 і після. Ціль: падіння щонайменше в 5–10 разів.
2. Під час роботи можна тимчасово ввімкнути лічильник запитів у `web/lib/prisma.ts` через Prisma Client extension `$extends({ query: { $allOperations } })` з інкрементом лічильника і логувати його в кінці кожного cron. Перед комітом прибери це або залиш за env-прапорцем `PRISMA_QUERY_COUNT_LOG=1`.
3. Наступний рахунок Prisma (1 грудня) має бути близько $10–20.

## 4. Правило на майбутнє (додати в `.cursor/rules/`)

Створи файл `.cursor/rules/db-query-budget.mdc`:

```markdown
---
description: Бюджет запитів до Prisma Postgres — кожен запит платний
alwaysApply: true
---

# Запити до БД коштують грошей (Prisma Postgres, оплата за кожну операцію)

- Нові cron: не частіше ніж раз на 15 хв без явного погодження з користувачем. Завжди писати в коментарі, скільки запитів до БД робить один запуск.
- Cron, що синхронізує дані з Altegio чи банку, бере лише вікно останніх днів. Повна історія — раз на добу вночі.
- Не викликати `upsert`/`update` в циклі по всіх рядках. Спершу один `findMany`, порівняння в пам'яті, потім запис лише змінених (`createMany`, батчі).
- Якщо даних для обробки немає, виходити до першого запиту в БД.
- Перед додаванням cron у `web/vercel.json` оцінити: запусків на місяць × запитів за запуск. Якщо виходить > 1 млн на місяць — обговорити з користувачем.
```
